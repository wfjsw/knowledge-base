# Launch the Python in the Hard Way

A launcher for Stable Diffusion WebUI sounds like the most innocent program imaginable: find Python, run the entry script, show a console. In reality the project spends thousands of lines on making that happen reliably for people who will never open a terminal, and who are running an app whose dependency graph exploded along with the AI boom. Much of what it does is specific to this one app, but the shape of the problems — finding a Python, trusting a broken environment, loading compiled extensions, surviving a hostile dependency ecosystem — extends to almost any Python project shipped to end users.

## What could possibly go wrong?

### There is no "python"

The user's machine has no trustworthy Python at all. The app ships no interpreter, so the launcher has to find one — and "find" means archaeology. Different webui forks bundle Python in different places (`py310\`, `python\`, `venv\`, a ComfyUI-style `..\python_embeded\`), and every location has been seen in the wild, so discovery is a hardcoded list of a dozen-plus candidate paths. Each candidate is *executed* to be validated, not trusted by name: a probe process runs a one-liner that exits 0 only for 64-bit CPython 3.10 (`sys.hexversion & 255 == 240 and sys.maxsize > 2**32`). A file that merely looks like python does not count. The strictness is not pedantry — users genuinely run pre-release and alpha Pythons, and 32-bit (i386) builds, and both look plausible at a glance while breaking in obscure ways. The probe exists so those machines fail fast with a clear message instead of after an hour of mysterious crashes.

```csharp
// run: python -c "import sys,os;os._exit(0 if sys.hexversion&255==240
//        and sys.maxsize>2**32 else 1)"   → exit code 0 is the only truth
```

When nothing is bundled, the launcher provisions: a `python` on PATH becomes a private venv inside the app folder; the Windows `py` launcher is tried for 3.10 / 3.11 / 3.12 in turn; if a venv attempt fails, even the half-made venv is cleaned up properly. Two details are worth noting. The PATH search deliberately skips the Microsoft Store aliases (`WindowsApps`), which would otherwise "find" a stub that opens the Store instead of running anything — a naive `where python` would have shipped a launcher that opens the Microsoft Store on half the machines out there. And all the probing is cached inside a transaction, so one launch pays for the archaeology only once.

### The inherited environment is a lie

Whatever the user's session hands us, we cannot trust it. A leftover `PYTHONHOME` from a machine that once had a different Python breaks a bundled one; a user-level `pip.ini` pointing at a corporate index breaks installs; a `GIT` or `GIT_PYTHON_GIT_EXECUTABLE` naming some other git breaks git integration; stray `SSLKEYLOGFILE`s pollute logs. There is also a whole genre of user who read instructions on the web and inserted things into the environment variable list — some of those variables work, some silently sabotage everything, and the launcher can never know which is which. So the environment is scrubbed and rebuilt by hand: `PYTHONHOME` / `PYTHONPATH` removed, `PATH` rebuilt front-to-back (launcher dir, app dir, git, python, toolchain `Library\bin`), `PATHEXT` and `ComSpec` pinned. Even `cmd.exe` is located explicitly rather than trusted from `PATH` — people have been seen removing `C:\Windows\System32` from it. `PATH` is the least trusted thing on the machine. Then a stack of Python behavior switches is forced on — `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`, `PYTHONNOUSERSITE=1` (the user's own site-packages must not leak in), `PYTHONFAULTHANDLER=1` so even a C-level crash produces a readable traceback.

Then the cache variables (`TORCH_HOME`, `HF_HOME`, `TRITON_CACHE_DIR`, `XDG_CACHE_HOME`, `MATPLOTLIBRC`, and a dozen more) are pointed at a local cache directory — deliberately set with "don't override" semantics, so a user who already configured something keeps their value. Network variables follow the same logic: pip index and mirrors are injected, but proxies and mirrors only when the user asked for them. The intent: nothing the machine believes that we didn't ask for may influence the run.

### Portable by design

This is the rule that shapes everything else. Any environment the launcher creates must be portable and deletable, with zero residue in the system — no system-wide Python, no `pip install` into the user's environment, no service, no autostart entry, no files written outside the app folder. Uninstall *is* deleting the folder, and that has to work. Some launchers in the wild get around missing prerequisites by asking users to install Python, Git, CUDA, or the VC++ redistributable themselves; this one actively avoids that — if the machine lacks something, a private copy is provisioned inside the app instead of an installer dialog. The rare exceptions are two OS-level toggles (long paths, UTF-8 code page, below), and those always ask the user first.

### The machine itself may be broken

Two machine-level failures are worth checking *before* any Python is spawned, because they fail fast and are fixable:

- **Long paths are disabled.** WebUI trees easily exceed 260 characters and suddenly die with bizarre "file not found" errors. The launcher checks `LongPathsEnabled` and offers to flip it via an elevated `reg.exe`.
- **The port is taken.** The target port is checked against a list of Windows-reserved ports *and* probed for live owners; the error carries the offending PID so the dialog can say "port 7860 is used by PID 1234 (chrome.exe)" instead of leaving the user staring at a web UI that never appears. A surprisingly common owner is an orphaned process left in the background from a previous session — other launchers are known to do exactly this, especially ones that elect not to show console windows, since with nothing visible there is nothing to close and the port stays held until reboot.

## Add some C to the problems

Python is the easy part; the ecosystem is C. Most of the "works on my machine" failures in this world come from compiled components — packages that are thin Python over C/C++ (`.pyd`). Their failure modes cluster into a few buckets, and the launcher defends against each:

- **Wrong versions.** A torch and a torchvision built against different ABIs refuse to load each other's binaries; a gradio version mismatch breaks the whole UI. The launcher validates the installed torch build against the selected engine before launch, and matches known-bad version pairs.
- **CUDA is really two versions.** The NVIDIA *driver* has a CUDA version, and the *torch wheel* ships its own CUDA runtime. They do not need to match exactly — the driver only has to be at least as new as the runtime the wheel was built against — but users routinely hit the failure where a torch built for newer CUDA silently refuses to initialize on an older driver. The launcher reads the driver's CUDA version from the graphics stack and compares it with the runtime version the installed torch reports, so the mismatch is caught before launch instead of failing minutes later at `torch.cuda`. The check is per-device, not just per-version, because there is a too-new edge as well: a recent GPU generation can demand a much newer driver even when the CUDA versions nominally agree. And the architecture has to fit in the first place — a CUDA build cannot be forced onto an AMD card, a ROCm build must match the GPU family, and the engine is validated against the actual silicon instead of whatever the user selected.
- **Wrong environments.** A 32-bit Python found on PATH is detected and flagged (`Pythonx86`) rather than failing cryptically mid-import. A Python minor mismatch is caught by the same probes. `PYTHONNOUSERSITE` stops a half-broken per-user site-packages from shadowing the private environment.
- **Wrong library versions.** The `.pyd` loads but binds to the wrong DLL — the classic is some unrelated application having shipped its own `zlib.dll` or `cudnn` where the process can find it, or the machine having a stale VC++ runtime. The missing VC++ redistributable is such a massive failure source in the wild — its symptom is a crash so deep inside a compiled library that nobody can read it — that the launcher checks for it specifically, on every launch, before anything else runs: it probes `vcruntime140.dll` and friends by actually attempting `LoadLibraryEx`. It is equally careful about DLL search order — the toolchain's `Library\bin` is added explicitly via `AddDllDirectory` instead of relying on inherited PATH order, so a random app's DLL can never be picked up.
- **Encoding.** Compiled code is especially sensitive to the machine's code page. If the app lives under a path with non-ASCII characters (a Chinese username is the canonical case), console decoding and file I/O misbehave unless the system is on UTF-8 code pages. The launcher detects the non-ASCII install path, compares the registry code pages against the *live* values (to catch "changed but not rebooted"), and offers an elevated `.reg` import to switch to UTF-8.

**Compilation.** Some packages simply have no working Windows wheel and must be built from source (bitsandbytes, xformers, Triton). Building requires the MSVC toolchain — but installing Visual Studio would violate the no-residue rule. So the launcher can fetch the MSVC build tools into its own folder and inject the whole compiler environment (`cl.exe`, Windows SDK paths, `INCLUDE`/`LIB`, `DISTUTILS_USE_SDK=1`) so even a from-source build stays private to the app. That said, the compiler is somewhat optional: the default is to prefer prebuilt wheels and only reach for a toolchain when a package genuinely has none.

**PseudoConsole.** One more subtle break: some programs inspect whether their stdout is a real console and change behavior — fancy CLI progress UIs, interactive prompts — and plain stdio redirection makes them dumb or broken. For the projects that need such a fancy interface, the process is attached to a pseudo-console (ConPTY): the program believes it has a real terminal, while the launcher still intercepts every byte for its own log and console. But it is not the default — it is offered per project. Normally the launcher just redirects stdin/stdout/stderr, because redirection is easier to handle and less buggy: three plain UTF-8 pipes, no terminal semantics to get wrong, no resize protocol, nothing to replay. The pseudo-console is the exception you opt into only when the program genuinely cannot live without it.

## Job Objects: no orphan processes

The webui spawns subprocesses freely — extension servers, workers, git and pip helpers — and a launcher that dies abnormally must not leave any of them behind. A crash, a killed window, or a shutdown while a worker is mid-download would otherwise leave stray `python.exe` processes holding files open, and for a portable app that is exactly the residue that makes "delete the folder" fail.

The mechanism is one flag: the launcher creates a Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and attaches the process tree to it at creation. When the launcher's job handle closes — gracefully or not, since Windows closes it automatically when the owning process dies — the OS kills every process in the job. A "stop" click and an abnormal death are therefore the same code path, and nothing lingers.

## Little Scary Extensions

The webui's real enemy is its own success: the extension ecosystem. Users install extensions from GitHub by the dozen, and every extension is a small independent project that brings its own dependencies, pins, and patches. The result is a whole swath of *competing* requirements converging on one Python environment: extension A needs gradio X while extension B needs gradio Y; extension C quietly upgrades torch to something the core doesn't support; extension D patches the same module as extension E. The worst variant is the quietest. Extensions declare torch versions all the time, and a naive `pip` resolving that request will happily install the *CPU* build from PyPI over the GPU build the launcher validated — no error, no warning, the user just suddenly has no CUDA, and the only symptom is that everything got fifty times slower. This is by far the largest dependency problem the launcher has to defend against. Any one of these can break the entire app — and the user, by definition, cannot debug dependency hell.

The launcher is the buffer between that chaos and the user. Duplicated extensions are detected and called out before launch. The core environment is kept stable so extensions can only add on top of it, never wreck it (next section). And when an extension does break something, the failure is matched against a catalog of known problems and turned into a plain-language dialog with a fix, instead of a wall of traceback. The user never has to know that the cause was "extension X pinned `torchvision==0.16`"; they just see what to do.

## Reaching a versioned consensus

To hold the line against that chaos, the launcher needs its own opinion about versions — independent of the environment it is launching.

- **Inventory without trusting pip.** It shells out to the chosen Python once to dump `sys.path`, then scans those directories for `*.dist-info` / `*.egg-info` folders to build a package table (name, version, python-version tag). Using pip itself for this would be both slow and fragile: enumerating packages through pip costs real seconds, and if pip is broken — its own dependencies damaged, its cache corrupted — the inventory fails exactly when it matters most. A broken pip must not blind the launcher.
- **Constraints, declared per fork.** Each fork declares its requirements as version constraints; at launch they are serialized to a temp file and handed to the package manager — pip *and* uv are both served, since uv increasingly does the actual installing.

```csharp
psi.Environment["PIP_CONSTRAINT"] = fileUri;
psi.Environment["UV_CONSTRAINT"]  = fileUri;
```

- **Critical packages are protected.** Certain packages are guarded so that nothing in the environment can modify them — a conflicting request is refused or redirected before it can downgrade or replace the torch or gradio the core was validated against. Torch is the prime example: the GPU builds live only on a special index, while the default PyPI torch wheel is CPU-only, so the launcher points pip at the GPU index and treats any request that would swap the validated build as hostile. And every launch re-verifies that torch still sees the GPU, so even a successful sneak-through is caught at the next start instead of silently costing the user their CUDA.
- **Some packages are redirected.** Sometimes the right package is a different one: upstream abandoned, the build broken on Windows, or a dependency that drags in something harmful. The launcher substitutes those — for example, a popular package whose declared extra dependency (an `ffmpeg` wheel) collides with the rest of the environment gets that dependency stripped. Lots of weird stuff lives in the real world, and each entry in the substitution table is a scar from one specific machine.

And when the process finally runs and something still breaks, the console log is piped through a catalog of problem matchers — small classes that each know how to recognize one failure in the log and how to fix it: rerun pip with the right flags, download a driver, edit a config file. A wall of stderr becomes a dialog with a working button. The philosophy, more than anything: an error should know what it is and how to fix itself.

## So: why the hard way?

Because "just run `python main.py`" is only true on the machine where it was written. The real audience installs nothing, reads nothing, and cannot be asked to resolve a version conflict — and the app they run is an ecosystem of competing dependencies held together by a Python interpreter that isn't even guaranteed to exist. Every defense above is a scar from a specific, witnessed failure: the Store-alias python, the 32-bit interpreter, the stale VC runtime, the wrong `zlib.dll`, the Chinese username on a legacy code page, the extension that tried to downgrade torch, the stray process left behind by a crash. A `.bat` file cannot do any of this; a launcher that must be reliable, portable, and residue-free for non-technical users has to be, in miniature, an operating system for one process. Launching Python is the easy part. Making the machine agree that this Python is *the* Python — that is the hard way.
